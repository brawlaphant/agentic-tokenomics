# Integrator guide: m014 Authority Validator Governance

**Mechanism:** Authority Validator Governance
**Canonical spec:** [`mechanisms/m014-authority-validator-governance/SPEC.md`](../../mechanisms/m014-authority-validator-governance/SPEC.md)
**Reference implementation:** [`mechanisms/m014-authority-validator-governance/reference-impl/m014_score.js`](../../mechanisms/m014-authority-validator-governance/reference-impl/m014_score.js)

## 1. What this mechanism does

m014 computes a composite performance score (`0..1`) for a validator based on up to three weighted factors: uptime, governance participation, and ecosystem contribution. The score is what governance uses to evaluate validators during PoA (Proof of Authority) transition — validators with `performance_score < 0.70` are flagged for review per [SPEC.md §5.3](../../mechanisms/m014-authority-validator-governance/SPEC.md). An integrator uses m014 to build a leaderboard, power a PoA transition dashboard, or flag probation-worthy validators in a governance report. The mechanism also emits performance flags that downstream tooling can surface in alerts.

The factor weights are:

- `uptime` × 0.4 — block signing rate over the trailing 30 days
- `governance_participation` × 0.3 — fraction of recent proposals voted on
- `ecosystem_contribution` × 0.3 — AGENT-004's assessed contribution score

## 2. What you give it

```js
import { computeM014Score } from "./m014_score.js";

const result = computeM014Score({
  validator: {
    address: "regenvaloper1chorus",
  },
  factors: {
    // Each factor is a number in [0, 1] or null/undefined if unavailable.
    uptime: 0.9999,
    governance_participation: 1.0,
    ecosystem_contribution: 0.985,
  },
});
```

**All factors are floats in `[0, 1]`.** Not percentages, not basis points, not 0-1000. If you're pulling from a Cosmos LCD that returns ratios in a different shape, normalize before calling. The function clamps inputs to `[0, 1]` but pre-normalizing upstream makes the input more auditable.

**Schemas:** [`m014_performance.schema.json`](../../mechanisms/m014-authority-validator-governance/schemas/m014_performance.schema.json) and [`m014_validator.schema.json`](../../mechanisms/m014-authority-validator-governance/schemas/m014_validator.schema.json).

## 3. What you get back

```js
{
  address: "regenvaloper1chorus",
  performance_score: 0.9955,   // 0..1, rounded to 4 decimals
  confidence: 1.0,             // 0..1, based on how many factors were present
  factors: {                   // factors echoed after clamp and null-propagation
    uptime: 0.9999,
    governance_participation: 1.0,
    ecosystem_contribution: 0.985,
  },
  flags: [                     // may be empty; see "performance flags" below
    // "below_performance_threshold",
    // "below_uptime_minimum",
    // "probation_recommended",
  ],
}
```

**Re-normalization on missing factors** — when a factor is `null`/`undefined`, its weight is removed from both the numerator and the denominator of the weighted sum. So a validator with only `uptime` present gets `(uptime × 0.4) / 0.4 = uptime` as the composite. This means "missing data" does not silently depress the score toward zero. Pinned by [`vector_v0_single_factor_uptime_renormalize`](../../mechanisms/m014-authority-validator-governance/reference-impl/test_vectors/vector_v0_single_factor_uptime_renormalize.input.json).

**Confidence by availability count:**

| Factors present | Confidence |
|---|---|
| 3 | 1.00 |
| 2 | 0.67 |
| 1 | 0.33 |
| 0 | 0.00 |

**Performance flags:**

| Flag | Fires when | Downstream effect |
|---|---|---|
| `below_performance_threshold` | `performance_score < 0.70` AND `confidence > 0` | Surface in performance report |
| `below_uptime_minimum` | `uptime !== null` AND `uptime < 0.995` | Surface in uptime alert |
| `probation_recommended` | Either of the above fires | Surface in probation queue |

The `confidence > 0` guard on `below_performance_threshold` is critical: a validator with no factors at all (`performance_score = 0`, `confidence = 0`) is a "no data" state, NOT a "poor performance" state. It does not get flagged for probation. Pinned by [`vector_v0_zero_factors_empty`](../../mechanisms/m014-authority-validator-governance/reference-impl/test_vectors/vector_v0_zero_factors_empty.input.json).

## 4. Common error modes

### 4a. Missing uptime must not trigger below_uptime_minimum

If `uptime` is `null`, the `below_uptime_minimum` check does NOT fire — the predicate is guarded by `resolvedFactors.uptime !== null`. Missing data is treated as "unknown", not as "bad". Pinned by [`vector_v0_missing_uptime_renormalize_high`](../../mechanisms/m014-authority-validator-governance/reference-impl/test_vectors/vector_v0_missing_uptime_renormalize_high.input.json).

### 4b. Strict inequality on the uptime boundary

A validator with `uptime = 0.995` exactly does NOT fire `below_uptime_minimum`. The predicate is `uptime < 0.995`, not `uptime <= 0.995`. Pinned by [`vector_v0_uptime_boundary_exact_0995`](../../mechanisms/m014-authority-validator-governance/reference-impl/test_vectors/vector_v0_uptime_boundary_exact_0995.input.json).

### 4c. Division-by-zero when all factors are missing

When all three factors are `null`, `totalWeight` is 0 and the composite would divide by zero. The reference impl short-circuits to `0.0` in this case. The validator is not flagged because `availableCount > 0` is false — the agent returns a harmless zero with zero confidence and no flags.

### 4d. Explicit 0 vs missing

A validator with `uptime: 0` is different from one with `uptime: null`:

- `uptime: 0` → counts toward `availableCount`, contributes `0 × 0.4 = 0` to the weighted sum, and fires `below_uptime_minimum` because `0 < 0.995`
- `uptime: null` → does NOT count toward `availableCount`, is excluded from the re-normalization, and does NOT fire `below_uptime_minimum`

If you're wiring to a data source that returns "0.0" for both "actually zero" and "unknown", normalize to `null` for the unknown case upstream.

### 4e. Review threshold comes from the SPEC, not a hardcoded constant

There is **no on-chain `POA_ELIGIBILITY_SCORE` parameter** today. The only thresholds encoded in [SPEC.md §5.3](../../mechanisms/m014-authority-validator-governance/SPEC.md) are `performance_score < 0.70` (review flag) and `uptime < 0.995` (probation flag). Integrators wiring dashboards should read these directly from SPEC.md §5.3 rather than inventing a separate eligibility constant — if governance later adopts a formal PoA eligibility parameter, it will be added to the SPEC and to [regen-data-standards](https://github.com/regen-network/regen-data-standards), and this doc will point to that canonical source.

## 5. Runnable example

The reference implementation ships with 7 test vectors covering the happy path (sample), the strict-inequality uptime boundary, the re-normalization branch (single factor), the missing-uptime guard, the zero-factors distinct state, and the below-threshold probation flow. The self-test discovers every vector in `test_vectors/` automatically:

```bash
node mechanisms/m014-authority-validator-governance/reference-impl/m014_score.js
```

Expected output:

```
m014_score self-test: 11 passed, 0 failed (across 7 vectors)
```

The test comparison has built-in tolerances — score within 0.0002, confidence within 0.01, sorted flag equality — so floating-point drift from a different Node runtime cannot produce a false failure. Every expected file was generated by running the same `computeM014Score` function that lives in the reference implementation.

The mechanism is registered in `scripts/verify.mjs`, so `node scripts/verify.mjs` runs the same self-test as part of CI.
