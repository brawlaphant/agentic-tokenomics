# Integrator guide: m012 Fixed Cap Dynamic Supply

**Mechanism:** Fixed Cap Dynamic Supply
**Canonical spec:** [`mechanisms/m012-fixed-cap-dynamic-supply/SPEC.md`](../../mechanisms/m012-fixed-cap-dynamic-supply/SPEC.md)
**Reference implementation:** [`mechanisms/m012-fixed-cap-dynamic-supply/reference-impl/m012_supply.js`](../../mechanisms/m012-fixed-cap-dynamic-supply/reference-impl/m012_supply.js)

## 1. What this mechanism does

m012 computes the per-period supply update for REGEN under a fixed hard cap. Each period the circulating supply either grows (mint) or shrinks (burn) toward a target set by the hard cap, a regrowth rate, and a set of multipliers that encode validator staking, stability commitments, and an optional ecological signal. The core equation is:

```
S[t+1] = S[t] + M[t] - B[t]
M[t]   = r * (C - S[t])
r      = r_base * effective_multiplier * ecological_multiplier
```

An integrator uses m012 when building a supply dashboard, a validator income projection, a governance proposal simulator, or anything else that needs to know "if the network burned X tokens this period, what would supply look like next period?"

## 2. What you give it

```js
import { computeSupplyPeriod } from "./m012_supply.js";

const result = computeSupplyPeriod({
  supply_state: {
    current_supply: "150000000000000",       // uregen, string (BigInt-safe)
    hard_cap: "221000000000000",             // uregen, defaults to 221T
    staked_amount: "75000000000000",         // uregen
    stability_committed: "0",                // uregen, default "0"
    m014_state: "INACTIVE",                  // INACTIVE | TRANSITION | ACTIVE | EQUILIBRIUM
    ecological_multiplier_enabled: false,
    // Only consulted when ecological_multiplier_enabled is true:
    // delta_co2: 25,
    // ecological_reference_value: 50,
  },
  burn_amount: "500000000000",               // uregen, string
  config: {
    r_base: 0.02,                            // base regrowth rate, default 0.02
  },
});
```

**Every amount is a string, not a number.** Supply values can exceed JavaScript's safe integer range (2^53 - 1 ≈ 9×10^15); uregen is micro-REGEN so 221M REGEN is 2.21×10^14, which is close enough to unsafe that the reference impl uses `BigInt` internally. Pass strings in, get strings out, never pass JS numbers.

**Schemas:** [`m012_supply_state.schema.json`](../../mechanisms/m012-fixed-cap-dynamic-supply/schemas/m012_supply_state.schema.json) and [`m012_period_record.schema.json`](../../mechanisms/m012-fixed-cap-dynamic-supply/schemas/m012_period_record.schema.json).

## 3. What you get back

```js
{
  next_supply: "151630000000000",     // S[t+1] as string
  minted: "2130000000000",            // M[t] as string
  burned: "500000000000",             // B[t] echoed
  regrowth_rate: 0.03,                // r = r_base * eff_mult * eco_mult
  effective_multiplier: 1.5,          // the phase-gated pick
  staking_multiplier: 1.5,            // 1 + staked/supply, clamped [1.0, 2.0]
  stability_multiplier: 1.0,          // 1 + stability/supply, clamped [1.0, 2.0]
  ecological_multiplier: 1.0,         // 1 when disabled, max(0, 1 - deltaCo2/ref) when enabled
  headroom_before: "71000000000000",  // (C - S[t])
  headroom_after: "69370000000000",   // (C - S[t+1])
}
```

**Phase-gated effective multiplier** — which multiplier drives regrowth depends on `m014_state`:

| m014_state | effective_multiplier |
|---|---|
| `INACTIVE` | `staking_multiplier` (pre-PoA world) |
| `TRANSITION` | `max(staking_multiplier, stability_multiplier)` (validators not punished during handover) |
| `ACTIVE` | `stability_multiplier` |
| `EQUILIBRIUM` | `stability_multiplier` |

The `max()` in TRANSITION is intentional — it protects validators during the DPoS → PoA handover so a validator who hasn't yet moved their stake into the stability tier still earns regrowth.

## 4. Common error modes

### 4a. Ecological multiplier collapse

When `ecological_multiplier_enabled: true` and `delta_co2 >= ecological_reference_value`, the eco multiplier becomes `max(0, 1 - 1) = 0` and minting halts entirely for that period. Burns still apply, so supply shrinks. This is pinned by [`vector_v0_eco_multiplier_co2_spike_halts_mint`](../../mechanisms/m012-fixed-cap-dynamic-supply/reference-impl/test_vectors/vector_v0_eco_multiplier_co2_spike_halts_mint.input.json).

### 4b. Zero supply guard

When `current_supply` is `"0"`, both `staking_multiplier` and `stability_multiplier` default to `1.0` (the `sFloat > 0` guard inside the reference impl), not `NaN`. Useful if you're simulating bootstrapping or a rebase from scratch. Pinned by [`vector_v0_zero_supply_guard`](../../mechanisms/m012-fixed-cap-dynamic-supply/reference-impl/test_vectors/vector_v0_zero_supply_guard.input.json).

### 4c. Burn exceeds supply + mint (underflow)

If `burn_amount` is larger than `current_supply + mint`, the computed `next_supply` would be negative. The reference impl clamps to `"0"` per Security Invariant 2 (Non-Negative Supply). This cannot happen on mainnet today, but the guard exists so a future bug producing a giant burn event cannot drive the ledger below zero. Pinned by [`vector_v0_burn_underflow_clamp`](../../mechanisms/m012-fixed-cap-dynamic-supply/reference-impl/test_vectors/vector_v0_burn_underflow_clamp.input.json).

### 4d. Cap inviolability

If the naive `next_supply` would exceed `hard_cap`, the reference impl clamps to `hard_cap`. This cannot happen with `r_base <= 0.10` (the validated upper bound) because the minting formula is `r * headroom` and `r * headroom < headroom` for any `r < 1`. The guard exists as defense in depth — a future refactor that widens `r_base` bounds cannot quietly break Security Invariant 1.

### 4e. r_base out of validated range

The reference impl throws `RangeError` if `config.r_base < 0` or `config.r_base > 0.10`. This is Security Invariant 5 from the SPEC. Integrators running parameter sweeps must catch this if they want to explore outside the validated band.

## 5. Runnable example

The reference implementation ships with 7 test vectors covering the happy path plus the ecological multiplier family, the phase-gated multiplier picker, the zero-supply guard, and the burn-underflow clamp. The self-test discovers every vector in `test_vectors/` automatically and verifies all 9 numeric output fields for each period:

```bash
node mechanisms/m012-fixed-cap-dynamic-supply/reference-impl/m012_supply.js
```

Expected output:

```
m012_supply self-test: 99 passed, 0 failed (11 periods across 7 vectors)
```

Every expected file was generated by running the same `computeSupplyPeriod` function that lives in the reference implementation. When the formula changes, the generator is re-run and the diffs land in the same PR as the code change.

The mechanism is also registered in the repository-level `scripts/verify.mjs` — `node scripts/verify.mjs` runs the same self-test as part of CI, so a break on m012 fails the whole repo verify job.
